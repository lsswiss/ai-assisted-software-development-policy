# Policy for AI Usage, Code Quality & Human Testing

For the use of AI at [Company Name], the following principles apply. They are aligned with the OWASP list **“Top 10 Risks for LLM Applications” (2025)**.

## 1. Responsibility and Liability of the Software Architect

### 1.1 Responsibility
The software architect must be able to explain every committed line of code at any time. Responsibility for the code remains fully with the human acting as software architect, who is accountable for the technology decisions made.

### 1.2 Employment-Law Liability
If the software architect or developer intentionally or through gross negligence violates the provisions of this regulation—especially, but not limited to, license checks, data protection requirements, or the obligation to review AI-generated code—they are liable under applicable law (in particular Art. 321e Swiss Code of Obligations) for resulting damages to the company or third parties.

## 2. AI Usage, Security, and Compliance Requirements

### 2.1 General Human Review Mandate
All output generated by AI tools or AI agents (source code, test cases, configurations, and documentation) is subject to a strict manual review obligation. No AI-generated content may be committed to version control (repository) or deployed to production without prior content, logic, and security review by the software architect or developer.

### 2.2 Prohibition of Production-System Access for AI Agents
Under no circumstances may AI agents receive access to production databases or production systems.

### 2.3 Isolation of Production Credentials and API Keys
Production credentials and API keys must remain strictly outside the scope of AI agents.

### 2.4 Tie Routes and Endpoints to Concrete Use Cases
API routes and Ajax endpoints are created exclusively for concrete use cases.

### 2.5 Central Input Validation
Each API route and Ajax endpoint must validate all inputs first through a central input-validation engine.

### 2.6 Prohibition of Unrestricted Database and Filesystem Exposure
No API routes or Ajax endpoints may be created that allow unrestricted read or write access to databases or to server disks/storage.

### 2.7 Mandatory License Review & Protection of Third-Party Rights
Before being checked into the repositories, AI-generated code is carefully reviewed by the responsible software architect to ensure it does not infringe upon third-party licenses, copyrights, or other intellectual property rights.

### 2.8 Bring Your Own AI (BYOAI)
The software architect pays for the AI tools they use.

### 2.9 Data Protection, Confidentiality, and Protection of Trade Secrets

#### Prohibition of Confidential Data Transfer
It is strictly prohibited to input personal data (e.g., customer, employee, or supplier data), credentials, passwords, trade secrets, or protected internal source code into external or public AI models, or to upload such data as prompt/context.

#### Requirements for BYOAI Tools (Commercial Use & Data Privacy)
When using Bring Your Own AI (BYOAI), only AI tools and plans may be used whose Terms of Service explicitly guarantee that entered data and prompts are not used for model training and are not permanently stored by the provider (e.g., Business/Enterprise tiers with model-training opt-out). The use of free consumer variants without privacy guarantees is prohibited for business purposes.

### 2.10 Copyright and Originality Threshold with AI Usage
All rights to AI-assisted code, test cases, and documentation belong exclusively to the company, regardless of whether they are created during or outside regular working hours. Purely AI-generated code does not meet international standards for copyright protection and must not be committed.

The software architect and involved developers must ensure through active, human, value-adding contribution (e.g., substantial revision, individual adaptation, or extension) that the code reaches the required level of originality to secure legal protection for the company.

### 2.11 Quality and Review of Code Comments
Comments generated by AI agents must not be adopted without review. All comments must be checked by the developer for correctness, precision, and added value, and revised or shortened manually where needed. Redundant, generic, or unclear AI explanations must be removed before commit.

### 2.12 Protection of Core Components and Engines
Existing core components and engines (e.g., API architecture, payment gateways, template or form engines, in-house code and function libraries) must not be replaced, bypassed, or fundamentally altered in behavior through AI-generated code, refactorings, or automatic AI version updates. Exceptions require prior written approval from management.

### 2.13 Labeling Obligation and EU AI Act Compliance

#### Transparency Toward End Customers
If AI-generated content (text, images, code) or interactive AI systems (e.g., chatbots) are used in [Company Name] products, they must be clearly and unambiguously labeled as AI-generated or AI-assisted for end users in accordance with the EU AI Act.

#### Prohibition of Forbidden Risk Classes
The use of AI systems that fall under prohibited categories of the EU AI Act (e.g., impermissible behavioral manipulation or biometric scoring) is strictly prohibited throughout the company.

### 2.14 Security of AI Components in Products (Prompt Injection & System Prompts)

#### Protection Against Prompt Injection (OWASP LLM01)
If AI agents or LLM interfaces are integrated directly into [Company Name] products or services, suitable technical and organizational controls must be implemented to protect against direct and indirect prompt injection. Untrusted user and third-party content must not be processed as trusted instructions without review. In particular, clear separation of system instructions and untrusted content, server-side authorization and validation checks for tool/function calls, and least-privilege principles must be ensured.

#### Protection of System Prompts (OWASP LLM02 / LLM06)
System prompts, instruction sets, and internal agent logic must be treated as confidential system components. They must be secured against information leakage and exfiltration via manipulation techniques (e.g., “Ignore previous instructions”).

#### Human-in-the-Loop & Agency Limits (OWASP LLM08)
AI agents must not perform autonomous, irreversible actions (such as deleting data, executing financial transactions, or changing system configurations) without explicit manual approval by a human user or operator.

## 3. Human Testing & Usability Standards
No automated or machine-based test replaces real human usage. Every software component must be manually tested before release for professional correctness, usability, and compliance with modern UX/UI industry standards.

### 3.1 Domain Logic and Fundamentals
- **Correct domain logic:** The software must be thoroughly tested by humans for complete and correct implementation of business processes and edge cases.
- **Security testing:** Manual tests and penetration tests to identify vulnerabilities should preferably be performed in test or staging environments.

### 3.2 Usability and UI/UX Industry Standards
During manual testing, the application must be checked against the following usability criteria:

- **Understandable empty states:** Where no data exists (e.g., empty tables, new accounts), understandable help pages or guidance text with clear next steps must be shown.
- **Accessibility (barrier-freeness):** The interface must be designed to minimize barriers (e.g., sufficient color contrast, keyboard operability, readable font sizes).
- **Contextual orientation:** At every step, the user must clearly know where they are, where they came from, and what to do next.
- **Clean and clear information architecture:** Menus, content, and functions must be logically structured without unnecessary nesting.
- **Clear user calls to action and wording:** Buttons and interaction elements must use clear, understandable labels (e.g., “Save” or “Order with Costs” instead of unclear labels). Language must remain precise and free of unnecessary jargon.

#### Dynamic Data Updates & Server-Driven HTML (htmx)
- **Standard:** For simple input/output use cases (e.g., classic full-page form submissions), regular page refreshes are allowed.
- **Dynamic updates:** For partial data updates (e.g., status changes, table reloads, push notifications), a full manual page refresh must not be required. The relevant region must be updated dynamically via the approved htmx framework (server-driven HTML hot reload).
- **Prohibited client frameworks:** To avoid unnecessary complexity, security risks, and maintenance overhead, JavaScript-heavy SPA frameworks (e.g., React, Angular, Vue) and outdated Ajax libraries (e.g., jQuery) are strictly prohibited.

- **Useful go-back paths:** Clear and reliable return paths must be provided (e.g., breadcrumbs, working back buttons) without losing application state.
- **Use of UI standard elements:** Established UI components and design patterns must be used so users can navigate immediately without onboarding.
- **Responsiveness for mobile devices:** The user interface must work on mobile devices and different screen sizes without rendering or functional errors.

Management reviews the regulations at least once a year. Any amendments will be submitted to the software architect for review and countersignature.
